### LC#33 — Search in Rotated Sorted Array [M]

**Pattern identified:** Binary search. User stated before coding: "the pattern seems to be the exact same as LC#704 after recognizing the array is rotated." Initial approach was to find rotation index k and unrotate the indices — redirected at hint 1.

**Target complexity stated:** O(log n) — correct.

**Approach:** Binary search where at each step one half is identified as sorted (via `nums[l] <= nums[mid]`). The target's position relative to that half's range determines which half to search. Key insight — exactly one half is always sorted — was not self-discovered; required concrete trace.

**Hints given:**
1. (Rung 1, ~5 min) "You don't need to find k first — at every step, one half is always sorted. Compare `nums[l]` and `nums[mid]`." Redirected away from unrotate approach.
2. Concrete trace `[4,5,6,7,0,1,2]` used to show that right half `[7,0,1,2]` is not sorted. User answered "no" and accepted the structure.

**LeetCode verdict:**
- First coded attempt had 4 bugs (see code quality notes). Not submitted until after bugs were identified in conversation.
- After all 4 fixes: Accepted, 196/196, 0ms, beats 100% C++ runtime.

**Final complexity:** O(log n) time — "search space halved at each step, log n iterations." User-derived. O(1) space — user-derived.

**Code quality notes:**
- `r = static_cast<int>(nums.size())` — off-by-one. Should be `nums.size() - 1`. Fourth occurrence across 4 weeks (W1 D4, W2 D4, W3 D4, W4 D2). Must appear without prompting at W4 D4.
- `else if (nums[mid] >= nums[r])` instead of plain `else` — structural error. When `nums[l] > nums[mid]`, the right half is always sorted; no condition needed. The `else if` evaluates false in the case it should fire, causing an infinite loop. Fix: plain `else`.
- `nums[mid] >= target` in right-half range check — wrong direction. Should be `nums[mid] <= target` (target must be ≥ lower bound to be in the range). Named and fixed after explanation.
- Missing `return -1` — pattern not carried over from LC#704 derivation.

### LC#875 — Koko Eating Bananas [H]

**Pattern identified:** Binary search on answer space — stated correctly before coding. "Expecting binary search." Pattern recognition accurate. Initial complexity claim of O(log n) was incomplete (missed inner loop), revised after probing.

**Target complexity stated:** O(log n) initially; corrected to O(n log M) after post-submission probing.

**Approach:** Binary search over eating speed range [1, max_pile]. For each candidate speed `mid`, `time_func` computes total hours via ceiling division: `(piles[i] / mid) + ((piles[i] % mid) != 0)`. If `time <= h`, record speed as candidate and search left (lower speed might also work); else search right (need faster speed). Fully self-derived — no hints on algorithm structure.

**Hints given:** None on algorithm. `long long` type explanation given directly (type knowledge, not algorithm knowledge).

**LeetCode verdict:**
- First submission: Missing `return k` — runtime undefined behavior. 
- Second submission: Runtime Error 122/127. Overflow: `1610612736 + 805306368` cannot be represented in `int`. Test case: `[805306368,805306368,805306368]`, h=1000000000.
- Fix: `long long sum = 0`, return type `long long`, `int time` → `long long time`.
- Third submission: Accepted, 127/127, 10ms, beats 38.8% C++ runtime.

**Final complexity:** O(n log M) time — outer loop searches speed range [1, max_pile], so O(log M) iterations; inner `time_func` iterates all n piles, O(n) per call; total O(n log M). M = max pile value, n = number of piles — two independent variables. User initially said "O(n) dominates" after seeing inner loop; arrived at O(n log M) after the question "how many times does the outer loop execute, and what is it searching over?" Score: user-derived with one correction prompt. O(1) space — stated correctly.

**Code quality notes:**
- Ceiling division `(piles[i] / mid) + ((piles[i] % mid) != 0)` — correct and idiomatic.
- Missing `return k` — no return statement in `minEatingSpeed`. Not caught until runtime.
- `long long` overflow — `sum` accumulated across large pile values exceeded INT_MAX (~2.1B). Integer width is a recurring risk on accumulation problems with large inputs.
- `time_func` as a named helper — clean separation of concerns.

## 4d. Scaffolding log

1. **"Both halves are sorted" misconception.** User said "both those halves are sorted and we can perform binary search on [l,mid] and [mid,r] consecutively — that would be 2 binary searches." Wrong — in a rotated array, exactly one half is sorted at any step. Corrected via concrete trace `[4,5,6,7,0,1,2]` — "is right half [7,0,1,2] sorted?" User: "no." Correction landed.

2. **`else if (nums[mid] >= nums[r])` instead of `else`.** User replaced plain `else` with a conditional. When `nums[l] > nums[mid]`, right half is always sorted — no condition needed. The `else if` fires false in exactly the case it should fire (right half sorted), causing infinite loop. Explained; fix applied.

3. **Right-half range condition direction `>=` vs `<=`.** `nums[mid] >= target` in `if (nums[mid] >= target && target <= nums[r])` — should be `nums[mid] <= target`. Named: "target must be ≥ lower bound to be in range [nums[mid], nums[r]]." Fixed after naming.

4. **Outer loop search space.** User said "outer loop executes log n times and is searching over piles." Wrong — outer loop searches eating speed range [1, max_pile], not the piles array. Explained via min_k/max_k initialization. User then derived O(n log M) correctly.

5. **"Ascending monotonicity" direction error.** User said feasibility function shows "ascending monotonicity in eating speed range." Wrong direction — as speed increases, hours needed decreases (monotonically decreasing). The structure is a step function: `[False,...,False,True,...,True]` — feasible above a threshold, infeasible below. Corrected; user acknowledged but did not restate correctly before session ended. Score 1.5 on closing check. Resurface D3.

6. **`long long` for `sum`.** User: "I don't know what sum should be." Given directly: `long long` — 64-bit integer, required when accumulation can exceed ~2.1B. Type knowledge, not algorithm knowledge.
